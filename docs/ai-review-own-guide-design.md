# 1-4 自前レビュー観点の設計案（2026-09-23）

根拠: `analysis-ecc-ablation-2026-09-23.md`（1-1）と `analysis-errors-2026-09-23.md`（1-2、1-3 を含む）。
対象: `/ai-review` の Claude 側レビュー（今の ECC `/code-review` の置き換え）と、強化版 `--deep`。

## 方針

1. **骨格は ECC から取る**（1-1 で効果を確認済み）: 変更ファイルは全文を読む／セキュリティを最初に見る／件数の上限を設けない／深刻度つきで全件を出す。
2. **報告経路の欠陥をふさぐ**（1-2 で誤判定の約9割がここ）: 閾値で捨てない、意図的に見えても抑制しない、攻撃者入力が絡む指摘は必ずセキュリティに分類する。
3. **過剰指摘は「消す」でなく「段を分ける」**（1-2 の F、1-3）: 部品の誤用は脆弱、設計パラメータの懸念は攻撃経路を示せたときだけ脆弱、示せなければ強化提案。
4. **一般的な内容だけを書く**: 特定のヘルパーの戻り値や、定数で分岐を固定する手口など、評価データ固有の知識は書かない。

## 観点（プロンプトに入れる内容の草案）

### 読み方
- 変更されたファイルは全文を読む。差分の行だけで判断しない。
- 変更コードが参照する設定値・ヘルパー・呼び出し先は、実装を開いて確かめる。名前や一般的な慣習から挙動を推測しない。
- 「テスト用」「意図的」「上流由来」「サンプル」に見えても、それを理由に指摘を省かない。意図が読み取れる場合は、指摘に注記として添える。

### 見るもの（優先順）
1. セキュリティ: 外部入力（リクエスト、ヘッダ、Cookie、ファイル、環境変数、外部 API の応答）がどこへ流れるか。出力先ごとに、使っている無害化が合っているか（HTML・シェル・パス・SQL・LDAP・XPath・セッション・ログ）。子プロセスの引数・環境変数・作業ディレクトリも注入先として扱う。弱い暗号・ハッシュ・乱数・Cookie 属性など、部品の選び方。
2. 正しさ: 条件の境界、null・空、例外とエラー処理、非同期の待ち忘れ、状態更新の順序、競合。
3. 設計・保守性: 責務の混在、重複、後から壊れやすい書き方。

### 判定の段
| 段 | 条件 | ゲートでの扱い |
|---|---|---|
| 脆弱（確定） | 外部入力が危険な出力先に届く経路をコードで示せる、または弱い部品を使っている | High。push を止める |
| 要確認 | 経路の一部を確かめきれない（呼び出し元が差分の外など） | 報告する。止めない |
| 強化提案 | 値域・鍵長・属性などの設計パラメータへの懸念で、具体的な攻撃経路を示せない | 報告する。止めない |
| 安全 | 経路が危険な出力先に届かない理由を、コードで示せる | 判定表にだけ載せる |

- 確信度で捨てない。迷ったら「要確認」に置く。
- 攻撃者の入力が関わる指摘は、動作のバグとしても書く場合でも、必ずセキュリティにも分類する。

### 出力契約
- 変更された全ファイルについて、判定（脆弱 / 要確認 / 強化提案 / 安全）と根拠1行の表を出す。
- 指摘は件数の上限なしで、深刻度・ファイル:行・問題・根拠（経路）・修正案を出す。

## ゲートの立ち位置と「要確認」の扱い（2026-09-23 ヒアリングで決定）

- 役割: ローカルの第1ゲート。コード品質を上げ、脆弱性をなくす。サブスクリプションの範囲で早く安く回し、手前で潰す。PR のレビュー Bot（クレジット消費）は第2ゲート。
- 見逃しと手間: 深刻度で変える。レポートは AI が読んで対応し、人は要点だけを見る。
- 要確認の扱い（C 案）: 未処理の要確認があると push できない。作業中の AI が1件ずつ調べ、直すか「安全、根拠は〜」と `latest.json` に記録すれば通せる。
- 「安全」判断の検証: 作業の文脈を持たない別のサブエージェントが、根拠がコードで成り立つかを確かめる。
- 人の承認（ア案）: 高リスクの要確認だけ。高リスク = 昇格ルールの危ないパス（認証・課金・DB・権限など）に当たる指摘、または外部入力がコマンド・SQL・パスに届く注入の指摘。機械的に判定する。
- 強化提案: 止めない。AI が安く直せるものは直し、それ以外は記録だけ残す。
- 成功の物差し: PR で Bot が見つける件数、ベンチのスコア、止まった回数と手間。

```
脆弱（確定） → 直す → /ai-review をやり直す
要確認       → AI が調べる → 直す、または「安全」と記録
                 → 別サブエージェントが根拠を検証
                 → 高リスク（ア）なら人が承認
強化提案     → 安く直せるなら直す、それ以外は記録
pre-push     → 未処理の「脆弱」「要確認」がなければ通す
```
